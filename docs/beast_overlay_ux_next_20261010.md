# Beast 조립 안내 UX: 최소 후속안

2026-10-10. **설계 메모이며 이번 변경에서 Unity/UI 기능을 추가하지 않았다.**
Windows 노트북 + Beast, Neckband 없음. 실물 정합은 미검증이다.

## 현재 구현과 구분

| 위치 | 실제 코드에 있는 것 | 아직 확인되지 않은 것 |
| --- | --- | --- |
| 카메라 진단 | `workspace_overlay.world_segments`의 A-B-D-C 둘레선, 목표 위 화살표 | 착용자의 눈에서 그 선이 실물과 겹치는지 |
| Unity SBS | `SbsGuidancePresenter`의 양쪽 눈 원, 현재 단계, 안내/보류 문구 | 후보 모드는 **A REF 고정**, 다음 나사로 자동 이동하는 완성 안내가 아님 |
| 상태 안내 | `GuidanceState`와 `TimedEvidenceGate`의 GUIDING/OBSERVING/OBSERVED/PAUSED 등 | 실제 체결력/토크/나사 풀림 검증 |
| 관제 | 영상 선택, 상태·이유, 카메라 투영/정합 미검증 표시 | 안경을 통해 보는 양안 광학 시야의 녹화가 아님 |

이 기반을 재사용한다. 새 UX 상태 머신, 새 서버, 제스처/음성 입력을 먼저 만들지 않는다.

## 자료에서 가져올 원칙

- Microsoft의 MR 품질 지침은 시야 밖 목표를 찾을 수 있는 시각/방향 단서를 권한다.
  따라서 목표가 보일 때는 직접 강조, 밖에 있을 때만 방향 화살표를 검토한다.
  이 문서는 HoloLens/Windows MR용으로, Beast 호환 SDK나 추적 성능의 증거는 아니다.
  [공식 품질 지침](https://learn.microsoft.com/en-us/windows/mixed-reality/develop/advanced-concepts/app-quality-criteria-overview#directional-indicators)
- PTC의 절차 편집 안내에는 단계별 위치 마커, 부품 표시, 확인 피드백이 있다.
  우리도 현재 작업 한 곳과 짧은 단계 피드백에 집중할 수 있다. Vuforia 도입을 뜻하지 않는다.
  [공식 절차 편집 안내](https://www.ptc.com/ja/success-paths/get-started-vuforia-expert-capture/setup/prepare-to-edit-procedures)
- Chu·Ko(2021)의 가려진 부품 조립 연구 초록은 가상/실물의 위치 차이가 손-눈 협응을
  저해할 수 있다고 설명한다. 정합이 불안정한 상태에서 큰 가상 부품을 덧씌우는 것은 후순위다.
  본문 전체를 검토한 것이 아니라 공개 초록의 범위이며, 이 연구가 Beast에서 검증된 것은 아니다.
  [논문 및 저자 소속기관 초록](https://scholars.nthu.edu.tw/esploro/outputs/journalArticle/An-experimental-study-on-augmented-reality/9957774689106774)
- 깊이를 자주 전환하는 표시가 불편함을 만들 수 있다는 MR 편안함 지침도 참고한다.
  HoloLens의 초점 거리 수치는 Beast에 적용하지 않는다. Beast의 화면 거리 설정이
  실제 광학 초점을 동일하게 바꾼다고 가정하지 않는다.
  [Microsoft 편안함 지침](https://learn.microsoft.com/en-us/windows/mixed-reality/design/comfort)

## 권장 화면과 구현 순서

1. **현재 목표 원 + A/B/C/D 문자.** 유효한 양안 투영이 있을 때 하나의 나사만 강조한다.
   색만으로 구분하지 않고 문자/모양을 함께 사용한다. 다른 나사는 기본적으로 표시하지 않는다.
2. **짧은 고정 화살표.** 목표 주변에서 나사를 가리키고 나사머리를 가리지 않게 배치한다.
   먼저 정적인 표시로 확인하고 계속 상하로 움직이는 애니메이션은 넣지 않는다.
   기존 카메라용 8~30mm 높이 화살표는 시험용 치수이지, 양안에서 검증된 UX 값이 아니다.
3. **얇은 윗면 둘레선, 필요할 때만.** A-B-D-C 연결을 재사용한다.
   나사 중심을 연결한 선은 상자 실제 외곽선과 다를 수 있다. 바닥/측면까지 직육면체로
   확장하려면 외곽 치수를 별도로 등록한다. 처음부터 실물 전체를 덮는 면은 만들지 않는다.
4. **시야 밖 목표의 가장자리 화살표는 나중에.** pose가 유효하고 목표 방향을 계산할 수
   있을 때만 사용한다. 지금 `CandidateProjection.Project`는 눈 시야 밖 점을 버리므로
   클리핑 전 방향을 전달하는 작은 계약 확장이 필요하다. 추적 소실을 시야 밖으로 위장하지 않는다.

상태별 표현은 기존 phase를 그대로 소비한다. 아래 문구는 UX 제안이며 번역 적용은 후속 작업이다.

| 기존 상태 | 표시 제안 | 하지 않을 것 |
| --- | --- | --- |
| GUIDING | 목표 원/문자, "나사 A에 드라이버를 대세요" | 여러 목표를 같은 강도로 강조 |
| OBSERVING | 목표는 유지, "드라이버 접근 확인 중" | 체결이 끝났다고 선언 |
| OBSERVED | "작업을 마쳤다면 드라이버를 떼세요" | 드라이버를 대고 있는 동안 다음 나사로 전환 |
| 다음 단계 확인 | 기존 acknowledgement를 짧게 표시하고 다음 목표로 전환 | UI 자체 타이머로 단계 전이 |
| PAUSED / stale / lost | 유효하지 않은 공간 표시는 숨기고 이유·복구 행동을 고정 안내 | 오래된 위치에 화살표를 남겨 놓기 |
| AWAITING_CONFIRMATION | "모든 나사 작업 관측됨. 최종 상태를 확인하세요" | 토크·체결 완료 보장 |

S0/S1에서는 상자/뚜껑의 정확한 공간 형상이 아직 등록되지 않았으므로 우선 문구만 유지한다.
정합 후보 A REF와 실제 작업 목표는 시연에서도 구분한다.

## 정합 뒤의 최소 파일 단위 작업

1. 서버의 검증된 pose와 `world_segments` 기하를 같은 frame/session/profile에 묶는다.
   `presentation_bridge.py`의 A 고정 참조를 단계별 목표와 섞지 않고 별도 계약으로 전환한다.
2. `CandidateProjection.TryProject`는 점의 양안 투영 계산에 재사용할 수 있지만
   현재 데이터 경로는 A 관측 전용이다. 계약/수신부와 양안 보정 검증 없이 임의의 선을 보내지 않는다.
3. `SbsGuidancePresenter`는 유효한 눈별 점/선만 그린다. 상태 판단은 서버에 남긴다.
   한 눈이라도 무효인 목표는 양안 모두 숨긴다. 선은 눈별 뷰포트 안에서 클리핑한다.
4. 관제에는 같은 목표 ID·보류 이유·카메라 투영을 보여 준다. 기존 "안경 시야 녹화 아님"
   구분을 유지한다. 새 대시보드나 AWS 스트리밍은 이 단계의 필수 항목이 아니다.

소프트웨어에서는 목표 전환/가림/끊김/오래된 데이터/한쪽 눈만 유효/화면 경계 테스트를 먼저 한다.
실착은 보정에 사용하지 않은 자세에서 A 원을 확인한 뒤 B-D, 화살표, 둘레선 순서로 확대한다.
새 UI를 추가할 때마다 긴 보정 전체를 반복하는 계획은 아니다. 다만 안경 재착용/화면 설정 변화는
기존 보정의 재사용 가능성을 별도로 확인해야 한다.
