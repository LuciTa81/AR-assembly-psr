# Beast 상태 안내 통합 (R4)

2026-09-28. **실물 없는 소프트웨어 구현·검사 완료 기록.**
이번 작업에서 카메라, Beast 착용 검사, 외부 서버를 실행하지 않았다.
실제 나사 정합과 새 안내 정책의 현장 성능은 H1/H2에서 확인해야 한다.

## 바뀐 동작

조립 상태 S0-S6와 안내 표시 상태를 분리했다. Python의
`OnlineStateFilter`만 조립 단계를 확정하고, Unity는 그 결과를 표시한다.
1학기 오프라인 HMM/Viterbi를 실시간에 새로 연결한 작업은 아니다.

| 상황 | 화면과 상태 동작 |
| --- | --- |
| 다음 작업 대기 | `GUIDING`: 현재 목표 나사의 작업 지시 |
| 목표에 도구 접근 | `OBSERVING`: 같은 목표 유지, 도구 접근 관찰 중 |
| 연속 접근 충분 | `OBSERVED`: 같은 목표 유지, 작업이 끝나면 도구를 떼도록 안내 |
| 도구가 보이는 상태에서 목표로부터 연속 이탈 | 다음 S 상태 및 다음 나사로 한 단계 이동 |
| 도구/끝점 누락, 인식 실패·시간 만료 | `PAUSED`: 미확정 관찰을 지우고 마지막 확정 단계 유지 |
| 마커 유실·연결 단절·좌표 만료 | 관련 복구 문구 우선, 위치 원 숨김 |
| D까지 관찰 | `AWAITING_CONFIRMATION`: 최종 사용자 확인 요청, 원 숨김 |

예: S2에서 A에 도구를 오래 대고 있어도 S3/B로 진행하지 않는다.
관찰이 충분한 뒤, 여전히 보이는 유효 도구가 A에서 멀어진 것을 확인해야
S3/B로 바뀐다. 단순 검출 실패는 정상 이탈로 해석하지 않는다.
한번 인식을 잃으면 이전 관찰을 이어 붙이지 않고 새 접근부터 확인한다.

이전 작업 알림은 별도 줄로 표시한다.
`Screw A interaction observed`가 남아 있어도 현재 지시
`Fasten screw B`와 B 원을 덮어쓰지 않는다.
알림의 남은 시간은 원래 전이 시각 기준이며 재수신으로 연장하지 않는다.

## 현재 초기값

`configs/realtime_viture_beast_aruco.yaml`에
`state_filter.guidance_policy: timed_v1`과 아래 값을 명시했다.

| 설정 | 값 |
| --- | --- |
| 상자/뚜껑 연속 관찰 | 300ms |
| 목표 나사 도구 접근 | 800ms |
| 도구 이탈 | 400ms |
| 연속 관측 간격 한도 | 350ms |
| 인식 결과 나이 한도 | 800ms |
| 이전 작업 알림 | 1200ms |
| 이탈 proximity score 상한 | 0.15 |

프레임 수가 아니라 원본 관측 시각으로 계산한다. 같은 YOLO 결과를 여러 번
받아도 시간이 누적되지 않는다. 과거·미래·누락된 시각, 오래된 결과,
다른 목표 또는 동률/더 강한 경쟁 목표는 진행 근거로 쓰지 않는다.
손에 의한 ROI 변화만으로 나사 단계가 진행되지는 않는다.

이 값은 소프트웨어 시작값이지 실측 최적값이 아니다.
실제 YOLO 간격이 350ms를 자주 넘으면 보류가 잦을 수 있다.
H2에서 조기 전이·전이 지연과 함께 측정하고 조정해야 한다.
정상처럼 보이는 지속적인 YOLO 오검출까지 제거한 것은 아니다.

## 로컬 도구 진단 창 (2026-10-06)

S2 정체를 관측하기 위한 선택적 진단 창을 추가했다. 인식 모델, 마커 조건,
전이 임계값과 유지 시간은 이 작업에서 변경하지 않았다.

- 실행 옵션: `run_realtime_server.py --diagnostic-preview`.
- 왼쪽은 현재 카메라 프레임과 ROI 설정으로부터 투영한 A-D 위치다.
  실제 나사 위치가 맞는지는 사용자가 확인해야 하며 눈별 AR 정합 결과가 아니다.
- 오른쪽은 유효한 YOLO 결과를 계산한 과거 원본 프레임이다. 해당 프레임의
  homography로 끝점과 ROI 위치를 그린다. 지연된 박스를 현재 영상에 붙이지 않는다.
- 초록색은 ROI 목표, 청록색은 검출 박스, 자홍색은 추정 드라이버 끝점이다.
  현재 상태, 마커 수, YOLO 원본 frame/age, 목표 점수와 접근/이탈 누적 시간을 표시한다.
- 추적 유실/오래된 결과/원본 프레임 누락 시 오른쪽 박스를 숨긴다.
  이 경우를 실제 드라이버 부재와 구분해 안내한다.
- 프레임은 최대 16개만 RAM에 보관한다. 진단 이미지 저장 기능은 없으며,
  `save_frames=true`와 함께 실행하려 하면 카메라 실행 전에 거절한다.
  일반 서버의 로컬 영상 제공 기능은 변경하지 않는다.
- `Q` 또는 창 닫기로 실행을 종료한다. 검사에는 `--max-frames`도 지정한다.
- 진단 수치는 `results.jsonl`의 `tool_diagnostic`에 남지만 영상은 기록하지 않는다.

검증: 원본 프레임/좌표 일치, 입력 불변성, 무효 관측 숨김, 버퍼 한도,
특이 행렬 처리 및 영상 저장 설정 거절 테스트를 추가했다. 전체 pytest 298개
통과. dummy 입력 12프레임으로 실제 Tk 창 실행/종료를 확인했다. 합성 화면의
픽셀과 텍스트 배치를 확인했으며 착용 검사는 별도다.

직전 실제 세션 `viture_aruco_rt_20261006_145621_23f49fc0b7aa` 재생에서는
S2 판정 802회 중 마커 불안정 536회, 유효하지 않은 관측 142회,
도구 부재/중복 판정 116회, 끝점 불명확 1회였다. A 접근 OBSERVING은
frame 269~270의 같은 YOLO 관측 1개뿐이었고 frame 271에서 마커가 3개로
줄어 누적이 초기화됐다. 800ms 관찰 완료는 없었다. 이 세션은 뚜껑 시험을
위주로 진행했으므로 위 수치를 YOLO 검출 정확도로 보고하지 않는다.

다음 실물 검사는 뚜껑을 닫고 마커/드라이버를 보이게 유지한 채 A 접근과
이탈을 구분한다. 실제 체결이나 토크를 검사하는 시험은 아니다.

### 첫 진단 실행 및 끝점 계산 수정

- 세션: `viture_aruco_rt_20261006_150755_7a437450e2f0`.
- 900프레임, 89.910초. S0 10, S1 4, S2 886프레임. S3 전이는 없었다.
- S2 표시 구간에서 마커 불안정 보류 438프레임, 무효 관측 209프레임,
  드라이버 부재/중복 보류 131프레임, 끝점 불명확 23프레임이었다.
- 정상 마커와 유효 YOLO가 동시에 있는 서로 다른 관측은 199개였다.
  검출 driver 수는 0개 107회, 1개 68회, 2개 이상 24회였다.
  이 수치는 사람이 라벨링한 검출 정확도가 아니다.
- A 접근은 frame 493~494(관측 492)와 frame 521(관측 520)에서 시작했으나
  새로운 관측이 이어져 800ms에 도달한 경우는 없었다. 도구 이탈 판정에도
  도달하지 못했다.
- 모든 프레임에 진단 수치를 기록했다. 필터 입력 재생은 900프레임 일치.
  영상 저장 0개, 외부 전송 없음, 정상 종료 후 Unity도 종료했다.
- 사용자는 착용 상태에서 노트북 진단 창 확인이 어렵다고 보고했다.
  실제 박스/끝점/나사 위치의 시각적 일치는 이번에 확인하지 못했다.
  이후 사용자는 Beast 안내에 집중하고, 분석은 기록된 수치를 우선 사용한다.

분석 중 `server/realtime/yolo_realtime.py`의 `long_axis_endpoints`에서
긴 변의 중점을 드라이버 끝점 후보로 사용하는 기하 오류를 확인했다.
20x100 직사각형에서 기대 후보 (10,0)/(10,100) 대신 (0,50)/(20,50)을
반환했다. 짧은 변의 중점 두 개를 고르도록 수정했다.

- 수평/수직/회전된 직사각형과 양쪽 손잡이 위치의 테스트 5개가 수정 전 실패,
  수정 후 통과했다. 전체 pytest는 303개 통과(23.39초).
- 검출 confidence, 거리 기준, 마커 조건, 접근 800ms/이탈 400ms는 변경하지 않았다.
- 이 수정은 끝점 **근사 계산** 오류를 고친 것이다. YOLO 박스가 잘못되거나
  마커가 끊기는 문제까지 해결한 것은 아니며 수정 후 실물 S3 전이는 미검증이다.
- `server/vision/build_yolo_features.py`의 과거 오프라인 계산에도 동일한
  패턴이 남아 있다. 이번 실시간 수정 범위에는 포함하지 않았고, 1학기
  benchmark/기록/성능 수치는 재계산하거나 변경하지 않았다.

  카메라/서버 정상 종료 후 Unity 시험 앱도 종료했다.

## 호환성과 안전 경계

- 이전 설정에 정책이 없으면 `legacy_frames`로 재생한다. 예전 기록을
  새 시간 정책의 검증 성공으로 바꾸어 해석하지 않는다.
- 새 기록은 원본 프레임/YOLO 시각, ROI 유효성, 단계, 목표, 문구, 표시 상태와
  알림을 남긴다. 같은 입력을 재생하면 해당 결과 전체가 일치하는지 검사한다.
- 늦게 도착한 전환/유실 이전 YOLO 관측은 무시하되, 그것을 받았다는 이유로
  복구 기준 프레임을 계속 뒤로 밀지 않는다. 정상 비동기 결과는 복구 가능하다.
- Unity의 선택적 `guidance` 필드는 생략/null이면 구형 메시지로 처리한다.
  명시적인 빈 객체/잘못된 형식은 거절한다. Unity JSON의 누락 객체 자동 생성
  동작은 표준 구조화 JSON reader로 필드 존재를 확인해 구분한다.
- 위치 안내에서는 보정/pose 문제의 안내가 도구 인식 보류보다 우선한다.
  S0/S1의 비위치 문구와 S6의 확인 요청은 눈 보정 없이도 표시할 수 있다.
- 실제 눈별 보정 프로필 로더는 아직 없다. 합성 SBS 시험에서 보이는 원은
  실제 나사에 맞춘 원이 아니며, 일반 실물 안내는 미보정 상태로 유지한다.
- S6는 자동 토크/체결 품질 판정이 아니다. 최종 확인 버튼·완료 저장 명령은
  이번 범위에 추가하지 않았다. 문구로 확인 필요성을 표시하는 단계다.

## 카메라 없는 재현

저장소 루트에서 기존 프로젝트 Python 환경을 사용한다.

```powershell
python -m pytest tests/realtime -q
dotnet run --project tests/unity/GuidanceTests.csproj -- --noresult
python tests/unity/guidance_fixture.py --output outputs/r4-demo/guidance.json
.\scripts\build_beast_unity.ps1
```

터미널1에서 합성 SBS 서버를 실행한다. 설정 파일은 존재하지 않는 새 경로를 사용한다.

```powershell
python tests/unity/serve_spatial_fixture.py --guidance --config outputs/r4-demo/preview.json
```

설정 파일 생성 후 터미널2에서:

```powershell
.\scripts\run_beast_unity.ps1 -SpatialPreviewConfig outputs/r4-demo/preview.json
```

노트북에만 시험 창을 띄운다. 서버는 첫 요청부터24초, 클라이언트는
화면 준비 후29초로 제한된다. 실제 카메라/이미지 스트림은 없다.
시험 창의 두 눈에 서로 다른 합성 좌표가 표시된다.
일반 텍스트 화면은 `python tests/unity/serve_snapshot_fixture.py --guidance`와
`.\scripts\run_beast_unity.ps1`로 확인하고, 검사 후 창을 닫는다.
일반 시험 서버의8765 포트에 기존 실행이 있다면 먼저 종료 여부를 확인한다.
