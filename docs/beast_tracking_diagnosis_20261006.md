## 2단계: 위치 수신 지연 개선

JSON 파싱과 화면 반영은 Unity 메인 스레드에서 하며, 메인 스레드 대기까지 포함한
전체 요청 시간을 기존 150ms 유효 시간 계산에 계속 넣는다.

- 서버, 보정값, 인식 임계값, 상태 수신, 눈별 보정점 Collect 경로는 변경하지 않았다.

  1초 timeout, 종료 취소와 늦은 응답 무시를 유지한다.
- 새 수신 로직 테스트를 포함해 C# 201개 통과.
- 실제 Unity HTTP/JSON/저장/취소 스모크 43개 검사 통과.
  Editor 첫 요청은 초기화/임포트 정지 시간을 배제하도록 유효하지 않은 예열 요청을 사용한다.
- 스모크의 정상 응답: 네트워크 2.25ms, 메인 스레드 반영 포함 4.0ms.

## 3단계: 카메라 주기와 OpenCV 계산 지연 분리

새 착용 자세 시험 없이 장치 입력과 기존 저장 사진을 조사했다.
카메라 속도 비교 중 기존 서버는 중지했고 카메라 0번만 순차적으로 열었다.

### 카메라 입력

| 요청 | 읽힌 형식/FPS 속성 | 실측 입력 간격 |
| --- | --- | --- |
| 기존 기본 설정 | YUY2 / 0 | 99.98ms |
| 30FPS 요청 | YUY2 / 30.00003 | 100.08ms |
| MJPG + 30FPS 요청 | YUY2 / 30.00003 | 99.72ms |

`set()` 성공과 FPS 속성만으로 실제 30FPS를 보장할 수 없었다.
이 연결/설정에서 관찰한 결과이지 Beast의 모든 모드가 10FPS로 제한된다는 결론은 아니다.
실효성이 확인되지 않은 FPS/FourCC 설정은 실행 코드에 추가하지 않았다.
이전 착용 비교 구간 전체 199프레임의 처리 시간은 평균 56.76ms였으므로,
100ms 입력 간격을 모두 인식 계산 탓으로 돌리지 않는다.

### 재현한 원인과 수정

설치된 `ultralytics/utils/__init__.py`는 DataLoader 충돌 예방을 위해
`cv2.setNumThreads(0)`을 호출한다. 실제 import 전 16스레드였던 OpenCV가
import 후 1스레드가 됐다. 이 설정은 YOLO뿐 아니라 같은 프로세스의 ArUco에도 적용된다.

`run_session`의 연속 presentation 모드에서만 YOLO 초기화 이후,
첫 프레임을 제출하기 전에 OpenCV 스레드를 `min(4, cpu_count)`로 설정한다.
CPU 수를 알 수 없으면 1을 사용한다. 현재 runner는 DataLoader를 사용하지 않는다.
프레임 처리 중 스레드 수를 바꾸지 않으며 비-presentation 실행은 변경하지 않는다.
보정 프로필, 검출 파라미터, 상태 판정 기준, 150ms 유효 시간은 그대로다.

입력: `Downloads/Beast_View_Retry_20261006_fd277ffc/workspace-view.png`.
동일 사진 반복 계산이며 현재 착용 중인 실시간 장면의 측정이 아니다.

  일반화하지 않는다. 표시 비율은 물리 디스플레이가 아닌 Unity Update 집계다.
- 사용자 체감: "확실히 줄었지만 아직 깜빡여".

수신 지연과 OpenCV 계산 지연의 개선은 확인했으나 편안한 연속 표시의 완료 조건은 미충족이다.
150ms 유효 시간과 마커/물리 pose 품질 기준은 그대로 유지했다.

### 오늘 종료 및 다음 재개

측정 후 사용자에게 안경을 벗어도 된다고 안내하고 이 작업의 Unity와 카메라 서버를 종료했다.
Chrome 대시보드 페이지는 남아 있을 수 있지만 실시간 입력은 중지된 상태다.
기존 로그와 보정/작업대 프로필은 보존했다. 오늘 추가 착용 시험은 없다.

집에서는 남은 위치 거부 원인을 저장 자료와 기하 테스트로 조사하고,
상태/유실 안내와 A-D 표시 연결을 모의 입력으로 검증할 수 있다.
새 환경에서 실제 정합을 확인하려면 카메라 인덱스, Full SBS/0DoF/확장 모드,
마커·상자 배치와 눈별 정합을 다시 확인한다. 물체나 마커를 옮겼다면 기존 등록을
그대로 검증 완료로 취급하지 않는다. 재현 자료가 없는 거부 구간은 다음 실측 과제로 남긴다.
