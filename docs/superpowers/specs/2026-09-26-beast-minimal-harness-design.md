# Beast 최소 하네스 설계와 개발 로드맵

작성일: 2026-09-26
상태: 사용자 승인 후 P0 하네스 코드와 전체 테스트 59개, 실제 영상 119프레임 재생을 검증했습니다.
OpenCV 차단은 해소됐으며, Beast 실카메라 150프레임 실행과 입력 로그 재생도 검증했습니다.
P0 실행 기준선을 확보했습니다. 추적 안정성/실제 표시 정합은 아직 검증하지 않았습니다.
Unity P1 클라이언트는 이후 구현/빌드하고 Beast 1920x1080 출력과 단절 처리를 검증했습니다.
착용 사용자가 원/문구 출력을 확인했습니다. 0DoF 표시 모드 고정은 대기 중이며
실제 정합/원격 연동은 아직 구현하지 않았습니다.
현재 결과: [P0 진행 기록](../../beast_harness_p0_status.md).
Unity 결과: [P1 진행 기록](../../beast_unity_p1_status.md).

## 1. 목표와 이번 범위

Windows 노트북과 VITURE Beast만으로 고정된 조립 대상의 다음 나사 위치에
원을 표시하고, 관찰된 조립 단계에 맞춰 짧은 작업 안내를 제공합니다.
이후 같은 세션의 카메라 영상과 상태를 별도 관제 화면에서 확인합니다.
안경에 카메라 영상을 크게 띄우는 것과 실제 나사에 안내가 겹쳐 보이는 것은
다른 완료 조건으로 취급합니다.

이번 하네스의 목적은 새로운 범용 프레임워크가 아니라 다음 네 가지입니다.

1. 같은 입력과 설정으로 문제를 다시 재현합니다.
2. 장치/모델/보정 누락을 시작 전에 알려줍니다.
3. 오래된 영상이나 추론 결과가 안내를 잘못 바꾸지 못하게 합니다.
4. 각 개발 단계에서 통과한 것과 아직 검증하지 못한 것을 기록합니다.

사용자는 1명, 인클로저는 1종, 작업대와 상자의 상대 위치는 고정합니다.
Neckband, JEV, 휴대폰 앱, 자유 이동 SLAM, 마커 교체, 체결 토크 판정은 제외합니다.
새 AWS 리소스, 영상 업로드, 운영 서비스 연결은 별도 승인 전에는 하지 않습니다.

### 설계 선택과 기존 문서의 관계

- 권장안은 기존 Python 파이프라인과 **얇은 Unity Windows 클라이언트**입니다.
  Unity는 최종 안경 표시를, 기존 브라우저는 카메라/점수 디버깅을 담당합니다.
- 브라우저만 사용하는 대안은 준비가 더 작지만, 이번에는 사용자가 요청한
  Unity 표시/보정 작업을 별도 클라이언트로 검증하는 방향을 택합니다.
- SafeOps 전체를 이식하는 대안은 운영 범위가 커지므로 채택하지 않습니다.

이 문서는 7월 Unity 설계의 범위를 줄이고, 같은 날짜의
`../plans/2026-09-26-beast-minimal-overlay.md` 중 브라우저 전용 출시/Unity 제외
부분을 대체합니다. 과거 계획은 작업 이력으로 보존합니다.
이 문서는 단계별 설계와 통과 기준이며, 첫 실행 계획은
`../plans/2026-09-26-beast-harness-p0.md`입니다. 이후 단계는 착수할 때 필요한
파일과 검사만 구체화하며, 전체 기능을 P0에서 미리 만들지 않습니다.

## 3. 최소 실행 구조

```text
Beast 카메라
  -> 노트북 Capture (최신 프레임 1개)
       -> ArUco/PnP -> 최신 pose -> 착용자 보정 -> Unity 원/문구
       -> ROI + YOLO evidence -> 로컬 OnlineStateFilter -> 안내 상태
       -> 로컬 세션 기록

원격 확장 단계에서만 추가:
  노트북의 선택 프레임 -> 원격 YOLO -> detection 응답 -> 같은 로컬 필터
  노트북의 상태 이벤트 + 저빈도 미리보기 -> 서버 -> 관제 웹 1페이지
```

빠른 위치 계산과 느린 인식은 실행 경로를 나눕니다. YOLO를 기다리는 동안
이미 움직인 머리에 맞지 않는 위치 원을 계속 표시해서는 안 됩니다.
단계 상태의 결정권은 노트북 필터 한 곳에 둡니다. Unity와 관제 서버는
별도로 상태를 추정하거나 다음 단계로 진행시키지 않습니다.

### 노트북 Python

- 기존 ROI용 homography는 유지합니다.
- 나사 높이를 포함한 3D 위치 계산에 카메라 보정과 metric Board/PnP를 추가합니다.
- 기존 YOLO를 로컬 기준선으로 사용하고, 이후 같은 입출력의 원격 adapter를 붙입니다.
- 추론 backend는 시작 시 선택합니다. 연결 실패 시 몰래 다른 모델로 바꾸지 않습니다.
- 인식이 끊기면 자동 전이는 멈춥니다. 추적/보정이 유효하면 마지막 확정 대상의
  위치는 계속 갱신할 수 있지만, 중단 표시를 합니다. 추적도 유실되면 원을 숨깁니다.

### Unity

- 우선 일반 Windows standalone 앱 한 Scene으로 시작합니다.
- 검은 배경, 목표 나사의 빈 원, 짧은 안내, 상태/중단 표시만 둡니다.
- 기존 로컬 HTTP snapshot을 순차 요청합니다. 이전 요청이 끝나기 전 새 요청을
  중첩하지 않습니다. 측정된 신선도 요구를 못 맞출 때만 WebSocket으로 교체합니다.
- 카메라/YOLO/상태 판정을 Unity에 중복 구현하지 않습니다.
- 대상 디스플레이, 해상도, 배율, 표시 모드를 고정하고 보정 프로필에 기록합니다.
- P1에서 direct/bypass 또는 native 0DoF의 실제 동작을 확인합니다. 장치의
  native 3DoF/화면 고정 기능과 애플리케이션의 위치 보정을 중복 적용하지 않습니다.
  설정값을 읽어 확인할 수 없으면 수동 확인 결과를 기록하고 정합 성공으로 판정하지 않습니다.
- VITURE Neckband용 Unity XR 예제를 필수 의존성으로 넣지 않습니다.
  Windows Glasses SDK는 표시 모드나 장치 제어가 실제로 필요한 경우에만 사용합니다.

### 원격 확장

- 첫 통합 시험은 같은 노트북의 별도 서버 프로세스로 수행할 수 있습니다.
- 실제 배포는 서버 1대에 Python API, 단일 YOLO worker, SQLite 이벤트 저장,
  정적 관제 페이지를 배치하는 구성을 우선 검토합니다.
- 추론은 요청한 클라이언트에 응답합니다. 공개 callback 주소나 SQS부터 만들지 않습니다.
- 관제는 저빈도 최신 JPEG 갱신으로 시작합니다. 이는 감시용 미리보기이며
  30 FPS 실시간 스트리밍 구현이라고 부르지 않습니다.
- 실제 외부 접속 전 TLS, 단말 인증, 세션 접근 제한, 업로드 크기 제한을 적용합니다.
  기존 로컬 디버그 HTTP 서버를 그대로 인터넷에 노출하지 않습니다.
- SafeOps에서는 요청 식별자, 모델 adapter, 설정/결과 기록 패턴을 참고합니다.
  군중 모델, Laravel, Django, KVS/IVS, SQS, RDS, 노드 풀은 초기 의존성에서 제외합니다.

## 4. 하네스 실행 모드

P0에서 doctor/replay/live-local 실행기를 추가하고 실카메라 캡처도 짧게 검증했습니다.
Unity 표시/정합을 포함한 전체 live-local 경험과 live-remote 구현은 아직 완료되지 않았습니다.

| 모드 | 목적 | 외부 의존성 | 합격 조건 |
| --- | --- | --- | --- |
| `doctor` | 실행 준비 상태 확인 | Python/장치 조회 | 누락과 실패 사유, 검사하지 않은 항목을 구분 |
| `replay` | 알려진 입력의 재현 | fixture와 해당 모델 | 유한 종료, 같은 증거 입력의 같은 상태 결과 |
| `live-local` | 실제 로컬 안내 | Beast, Unity, 로컬 모델 | 캡처/정합/전이를 별도로 검증 |
| `live-remote` | 원격 YOLO와 관제 | 승인된 서버/네트워크 | 지연/끊김에도 잘못된 자동 전이가 없음 |

재생은 두 층으로 구분합니다. feature/message fixture는 카메라/GPU 없이 상태와
UI 계약을 검사하고, 영상 fixture는 실제 영상 파이프라인을 검사합니다.
GPU/라이브러리 차이까지 영상 추론의 완전한 bitwise 일치를 보장하지 않습니다.

구현 전 SessionFrameSource는 반복 재생 중 원래 ID/시간을 유지하지 않았습니다.
P0에서 원래 ID/시간을 보존하고 자동 반복을 제거해 한 번 재생 후 종료하도록 수정했습니다. 다시 실행하면 새 프로세스와
새 session_id를 사용합니다. 필터, ROI 누적값, 이전 H, YOLO pending/result와
확인 표시는 전부 새로 생성합니다. 무중단 세션 교체나 복잡한 epoch 관리자는 만들지 않습니다.
프레임 누락은 조용히 건너뛰지 않고 기록합니다.

## 5. 데이터 계약과 안전 규칙

### 프레임과 시간

- `session_id`, `frame_id`, `calibration_profile_id`를 묶어서 식별합니다.
- 로컬 수신 시각은 노트북 monotonic clock으로 기록합니다. 실제 센서 노출 시각을
  제공받지 않았다면 capture-to-display 전체 지연을 측정했다고 부르지 않습니다.
- pose와 homography에는 생성에 사용한 frame_id를 붙입니다.
- 서로 다른 PC의 monotonic 값 또는 wall clock을 직접 빼서 지연을 계산하지 않습니다.
- YOLO의 원본 관측 시각을 보존합니다. 만료 초깃값은 `yolo.max_age_ms=800`이며,
  기존 약 10 FPS에서 8프레임을 허용하던 설정의 시작점일 뿐 검증된 최적값은 아닙니다.
  위치 원의 pose age 150 ms와는 별개입니다. 음수 age/미래 frame ID는 거부합니다.

### UI snapshot

- 기존 `OverlayMessage`의 상태 필드는 보존하고, 새 버전으로 pose sequence,
  상태 version, 보정 profile, `target_visible`, 표시 좌표, pose age를 추가합니다.
- Python과 Unity는 같은 버전/세션의 snapshot만 적용합니다.
- `assembly_state`와 `ui_status`를 구분합니다. 예를 들어 `S2`에서 추적이
  사라져도 `S2`는 유지하며 `ui_status=TRACKING_LOST`로 원만 숨깁니다.
- UI 상태는 STARTING, CALIBRATING, GUIDING, OBSERVED, PAUSED,
  TRACKING_LOST, COMPLETE로 제한합니다.
- OBSERVED는 해당 나사의 작업 증거를 관찰했다는 표시입니다. 바로 다음 나사
  원으로 바꾸는 신호가 아닙니다. 도구 이탈 확인과 현재 대상 표시를 일관되게 처리합니다.
- 유효 pose/보정이 없거나 좌표가 비정상/화면 밖이면 위치 원을 숨깁니다.
- 초기 실험에서는 pose age 상한을 150 ms로 두되 합격 성능을 보장하는 수치로
  쓰지 않습니다. 요청 왕복시간과 Unity 수신 후 경과시간을 보수적으로 포함해
  만료시키고 실제 움직임 시험으로 허용 범위를 조정합니다.
- 같은 pose sequence를 다시 수신해도 표시 수명을 연장하지 않습니다.
  서버가 응답하더라도 capture가 멈췄으면 원이 만료되어야 합니다.
- P1-P3에서 localhost 명령 경로 하나에 pause/resume, 보정점 입력, 최종 확인을
  단계별로 추가합니다. reset은 초기에는 실행 종료 후 새 세션 시작으로 처리합니다.
  명령에는 session_id와 command_id를 붙이고 Python만 상태를 적용합니다.
  처음에는 노트북 버튼/키보드로 조작하며 손동작/음성 입력은 만들지 않습니다.

### 추론과 큐

- 요청마다 observation ID, 원본 frame_id, 세션/보정 식별자를 붙입니다.
- 원격 응답의 bounding box는 해당 프레임의 homography로 변환합니다.
  현재 프레임의 homography와 오래된 검출을 섞지 않습니다.
- 프레임별 변환 기록을 제한된 크기로 보관하고, 이미 만료/삭제된 프레임의
  응답이나 순서가 역전된 응답은 버립니다.
- 같은 관측을 다시 받아도 확인 횟수, 머무름 증거, latch나 전이 이벤트를 늘리지 않습니다.
  캐시된 검출을 화면에 보여주는 것과 새로운 상태 증거로 소비하는 것은 구분합니다.
- 원본 프레임의 marker validity도 검사합니다. fallback H에서 만든 검출과
  마지막 추적 유실 이전의 늦은 결과는 복구 후에도 전이 증거로 쓰지 않습니다.
- 추적 유실/검출 만료 시 미확정 후보를 초기화하되 확정된 조립 단계는 유지합니다.
  P3에서는 새롭고 유효한 관측으로 연속 머무름과 이탈을 판단합니다.
  검출 실패, 타임아웃, 마커 유실 자체를 정상 도구 이탈로 취급하지 않습니다.
- 추론은 세션당 처리 중 1개와 대기 중 최신 1개만 유지합니다.
  YOLO가 느려졌다고 모든 과거 프레임을 FIFO로 쌓지 않습니다.
- 미리보기/검출은 최신값 중심이고, 확정 상태 이벤트는 유실 없이 따로 기록합니다.
  서버 업로드 재시도는 event_id로 중복 저장을 막습니다.
- P4에서 bbox는 원본 raw 이미지의 pixel xyxy로 반환하고 이미지 크기, 클래스 이름,
  모델/설정 식별자, schema version을 함께 보냅니다. 서버 resize/crop 좌표를 그대로
  보내지 않으며 성공한 빈 검출과 추론 오류를 구분합니다.
- P4에서 로컬 영속 기록 -> 재전송 -> 서버 저장 완료 ACK -> 전송 완료 표시를
  구현합니다. state_version이 낮은 늦은 이벤트로 최신 상태를 되돌리지 않습니다.
  관제의 읽기 권한과 단말의 쓰기 권한은 분리하고 운영 SafeOps 토큰을 공유하지 않습니다.

### 재현 기록

- 세션별 새 출력 디렉터리를 만들고 기존 세션 파일을 덮어쓰지 않습니다.
- 설정 사본, 코드 revision, 모델 hash, 보정 profile, 입력 모드, 상태 이벤트,
  프레임 ID, 처리 지연, 드롭 사유를 기록합니다.
- `save_frames=false`인 로그만으로 영상 재생이 가능하다고 하지 않습니다.
  시험 녹화의 범위/보관 위치는 사용자에게 알리고 기본적으로 로컬에 보관합니다.
- `yolo_age_ms`에 frame 개수가 들어가는 기존 단위 문제도 이 단계에서 수정합니다.
- 재생용 입력에는 필터에 실제 전달한 feature/관측 ID/유효성과 실효 설정을 저장합니다.
  판단용 float는 반올림하지 않습니다. 표시용 소수점 축약은 별도입니다.
- P0에서는 전이 이벤트를 flush/fsync한 뒤 새 상태를 외부에 게시합니다. 저장 실패 시
  실행을 중단하고 오류를 보고합니다. 임의 시점의 자동 이어하기나 원격 저장소는 만들지 않습니다.
  프로세스 재실행은 새 session이며, 전원 장애까지 무손실이라고 보장하지 않습니다.

### P0에서 먼저 통과시킬 검사

1. 모델/fixture 경로 누락 시 서버를 반쯤 실행하지 않고 사유와 함께 종료합니다.
2. 카메라 목록 조회 실패와 카메라 미발견을 구분합니다.
3. 유한 재생은 끝나며, 재실행은 상태/시간/이벤트를 새 세션으로 초기화합니다.
4. 같은 feature fixture의 상태 전이와 이벤트가 반복 실행에서 일치합니다.
5. marker invalid, stale detection, 잘못된 세션 입력에서는 자동 전이가 없습니다.
6. 로그의 시간 단위가 맞고 기존 출력은 덮어쓰지 않습니다.
7. 같은 관측을 세 번 주거나, 후보 두 번 뒤 긴 마커 유실과 한 번의 관측만 주어도 진행하지 않습니다.
8. 입력 기록을 다시 읽었을 때 임계값 근처의 상태 결과와 전이 목록이 일치합니다.

P0는 3D 정합, 새 모델 학습, 원격 배포를 포함하지 않습니다.
순수 상태/계약 테스트와 실제 영상/하드웨어 시험을 나눠 실행 결과를 보고합니다.

## 7. 보정과 사용자 확인이 필요한 부분

- 마커의 검은 외곽 기준 실측 크기, board 내 위치, 나사 A-D XYZ를 직접 측정합니다.
  사진에서 대략 읽은 매트 눈금을 보정값으로 확정하지 않습니다.
- 상자 위치를 고정할 표시/지그가 필요합니다. 상자를 옮겼다는 사실을 알려주는
  별도 검출기는 초기 범위에 없으므로 이동 후 사용자 재설정/재검증을 요구합니다.
- 카메라 intrinsic은 실제 사용할 해상도/영상 모드에 대응해야 합니다.
- 카메라 투영점이 맞는 것과 눈에 맞는 것을 따로 시험합니다.
  제한된 작업 거리에서 9점 display mapping을 시험할 수 있지만, 이를 모든 깊이와
  머리 이동에 통하는 양안 AR 보정이라고 부르지 않습니다.
- 디스플레이 모드/눈별 출력 가능성을 먼저 확인합니다. 단순 복제 화면을 양안
  정합 완료로 간주하지 않습니다. 복시/오차가 크면 해당 광학 경로는 통과하지 못한 것입니다.
- 안경 재착용, 고개 이동, 정상 작업 거리, 마커 가림 후 복구를 각각 확인합니다.
  정합이 특정 자세에서만 맞으면 시연 가능 범위를 그 조건으로 제한해 기록합니다.
- 합격 오차는 실제 나사 크기와 간격, 구분 요구에 따라 실험 전에 정합니다.
  카메라 reprojection error와 착용 상태의 mm 오차를 분리하고 검증점의
  median/P95/최대 오차 및 측정 방법을 기록합니다.

## 8. 기대 결과와 제외한 비용

P0의 결과는 재현 가능한 실행/검사/로그 묶음입니다. P1은 시험 원을 안경에
출력하는 데모이며, 실제 물체에 정합한 결과는 P2를 통과해야 합니다.
P3에서는 A에서 작업하는 동안 A 표시를 유지하고, 유효한 이탈 증거 후 B를
안내합니다. S6 이후에는 사용자의 최종 조립 확인을 요청합니다.
P4 관제 화면은 작업 영상, 확정 단계, 다음 작업, 추적 상태, 마지막 수신 시각,
전이 기록만 보여줍니다. 그 영상은 카메라 시점이며 착용자의 정확한 눈 시야가 아닙니다.

P0-P3은 신규 서버 임대를 전제로 하지 않습니다. 추가 준비물은 평평한 보정판,
치수 측정 도구와 상자 고정 수단입니다. Unity는 사용 주체의 라이선스 조건을
확인합니다. 서버/GPU 임대, 외부 전송/보관 비용은 P4에서 부하 측정 후 별도 승인합니다.
기존 SafeOps 운영 계정/토큰/서버는 자동으로 가져다 쓰지 않습니다.

## 9. 설계 당시 확인 기록

실행한 검사:

```text
Python 3.12.14 -B -m unittest tests.realtime.test_beast_device_check -v
Ran 8 tests ... OK
```

추가로 import 가능 여부, worktree/main 모델 경로, Unity 프로젝트 경로와
현재 소스 구조를 읽어 확인했습니다. OpenCV 등이 없어 전체 실시간/영상 테스트는
실행하지 않았습니다. 이번 문서 작성으로 모델/상태 코드, 패키지, Unity 프로젝트,
서버 설정은 변경하지 않았고 commit/push도 하지 않았습니다.

이 절은 구현 전 기록입니다. 이후 P0 코드/선택 검사/feature 재생을 구현했으며,
최종 결과와 환경 제약은 [P0 진행 기록](../../beast_harness_p0_status.md)에 있습니다.
