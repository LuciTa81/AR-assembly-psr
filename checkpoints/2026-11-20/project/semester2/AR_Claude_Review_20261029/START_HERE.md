# AR 조립 안내 프로젝트: Claude 검토 자료

작성일: 2026-10-29. 현재 작업 폴더의 코드와 기존 실험 문서를 대조한 인수인계 자료다.
이번 정리 과정에서는 카메라, Unity Player, 외부 AI를 실행하지 않았고 새 실기기 성능을 측정하지 않았다.

## 1. 먼저 알아야 할 결론

**단계 안내와 관제, SBS 표시 및 보정 수집 도구는 구현되어 있다. 하지만 움직임과 거리에 걸쳐 실물 나사에 정확히 붙는 양안 오버레이는 아직 검증되지 않았다.**

- 1학기의 오프라인 HMM 성능과 현재 실시간 성능은 별개다.
- 현재 실시간 기본 정책은 HMM Viterbi가 아니라 `timed_v1` 기반 증거 누적·접근·이탈 판정이다.
- 카메라 영상에 원을 그리는 것과 실제 눈에서 나사에 원이 겹치는 것은 별개다.
- 수동으로 두 눈의 원을 맞추는 시험은 여러 차례 성공했다. 자동 정합의 일반화 성공을 뜻하지 않는다.
- 자동 A 원 추적에서 사용자는 대략적인 위치 일치와 심한 깜빡임을 보고했다. 개선 후에도 깜빡임이 남았다.
- 마커 모서리 기반 추적 후보를 오프라인으로 비교했지만, 기존 정상 관측을 잃는 문제 때문에 실시간으로 활성화하지 않았다.

## 3. 목표와 제약

제목 후보: **작업 단계 인식 기반 AR 조립 안내 시스템**.

고정 작업대에서 상자 배치, 뚜껑 닫기, 나사 A/B/C/D 작업을 관찰하고, Beast 안경에 현재 단계와 다음 작업 위치를 안내한다. 노트북 브라우저에서는 카메라 영상, 단계, 보류 이유를 함께 확인한다.

| 항목 | 현재 조건 |
| --- | --- |
| 장치 | Windows 노트북 + VITURE Beast. Pro Neckband 없음, 도입 계획 없음 |
| 영상 입력 | Beast UVC 카메라, OpenCV. 현재 설정 1280x720, DirectShow |
| 표시 | Unity Windows standalone. 일반 2D 또는 Full SBS + 0DoF |
| SBS | 전체 3840x1080, 눈별 1920x1080 기준. 연결 후 실제 모드 확인 필요 |
| 착용 조건 | 사용자 보고: 전체 PD 64mm, Beast 도수 렌즈, Extra Large / 4.5m |
| 대상 | 고정 상자와 작업대 마커. 나사 평면 약 60mm 높이, 나사 간격 약 110mm |
| 우선순위 | 최소 구현, 실제 동작과 실패 이유를 명확히 표시. 반복 보정만 늘리지 않기 |
| 제외 | 임의 물체 인식, 완전한 markerless 6DoF, 실제 체결 토크 판정, 클라우드 필수화 |

안경의 화면 거리 설정을 물리적 초점거리 또는 보정된 가상 카메라 거리와 동일시하지 않는다. 착용 위치가 바뀌면 눈과 카메라/디스플레이 사이 관계가 달라질 수 있다. 마커는 안경 카메라의 자세를 알려줄 수 있지만 눈의 착용 위치를 직접 측정하지 않는다.

## 4. 현재 파이프라인

```text
Beast UVC 카메라 -> FrameSource (카메라 입력 공유)
  |
  +-> ArUco homography -> ROI 특징 + 비동기 YOLO
  |     -> OnlineStateFilter / TimedEvidenceGate
  |     -> 동일 단계 snapshot -> Unity 안내 / 브라우저 관제 / 수치 로그
  |
  +-> 선택적 PresentationBridge
        -> 보정 카메라 + 작업대 프로필 -> metric pose / 관측 상태
        -> 로컬 observation 서버 -> Unity CandidateProjection -> SBS A 참조 원
        -> 카메라 영상 투영 진단 (A-D 연결선 / A 화살표)

별도 오프라인 도구:
  관측 수집 -> 눈별 DLT / 단순 양안 모델 비교
  저장된 검출 모서리 -> 기존 중심 방식 / 새 모서리 후보 비교
```

여기서 단계 인식용 top-view warp, metric pose, 카메라-눈-디스플레이 정합은 서로 다른 계산이다. 브라우저에 보이는 카메라 투영 영상은 착용자의 양안 시야를 녹화한 것이 아니다.

## 5. 구현 상태

| 영역 | 구현·확인된 범위 | 아직 보장하지 못하는 것 |
| --- | --- | --- |
| 입력 | 카메라 선택/조회, 실제 Beast 영상 수신, 입력 오류 처리 | 카메라 번호 영구 고정. 재연결 시 번호가 바뀐 적 있음 |
| 작업 인식 | S0-S6, ROI + YOLO, 도구 접근/유지/이탈, 시간 기반 안내 상태 | 다양한 시점·조명에서의 정확도, 실제 조임 완료 |
| 안내 | 단계·목표·보류 이유, Unity 2D/SBS 문구, 브라우저 상태 공유 | 최종 UX 사용자 평가 |
| 카메라 위치 | 카메라 보정, 마커 중심 기반 pose, 나사 XYZ 등록, 투영 진단 | 모든 마커 조합에서 연속 안정 추적 |
| 양안 표시 | 좌우 채널 확인, 눈별 원 조절, 동시 관측 PAIR 저장, 후보 자동 투영 | 거리·자세·재착용에 강한 정합 |
| 공간 UI | 카메라 영상에서 나사 연결선/화살표. SBS 자동 A 참조 원 | 실제 눈에서 A-D/모든 선의 정합, 단계별 공간 목표 전환 |
| 오프라인 추적 | 3개 이상 마커 모서리 pose 후보와 수치 비교 | 실측 geometry 및 live 소비자까지 연결한 검증 |
| 서버 확장 | 로컬 HTTP, 상태/수치 로그와 관제 | SafeOps/AWS/KVS/IVS/원격 AI 운영 연동 |

**A 참조 원은 A에 고정된 시험 표시다. 단계 문구가 B/C/D로 넘어갔다고 자동 원도 해당 나사를 가리키는 것은 아니다.**

상태 의미: S0 빈 작업대, S1 상자 배치, S2 뚜껑 닫힘, S3/S4/S5/S6 각각 A/B/C/D 작업 관측. 마지막은 순서 관측 및 사용자 확인 대상이지 체결 품질 보증이 아니다.

현재 `timed_v1` 설정: placement 300ms, engage 800ms, release 400ms, max_gap 350ms, max_age 800ms, ack 1200ms. 도구 검출만으로 즉시 다음 단계로 넘어가는 설계가 아니다. 도구가 안 보이는 것과 유효하게 목표에서 이탈한 것을 구분한다. 설정 파일에는 과거 정책용 값도 있으므로 실제 소비 경로를 확인해야 한다.

## 6. 정합 관련 핵심 근거

### A. 마커 개수보다 기하가 문제인 구간

현재 중심 기반 pose는 최소 4개 중심을 사용한다. 0/1/2가 같은 줄에 있으므로 `0,1,2,4`처럼 네 개가 보여도 3점 공선으로 homography 계산이 퇴화할 수 있다. 단순히 최소 개수만 낮추는 해결책과 모서리 정보를 사용하는 해결책은 다르다.

최신 오프라인 모서리 후보는 등록된 마커 3개 이상의 12개 이상 모서리를 사용한다. 다만 검은 외곽 한 변 70mm를 가정하고, 기준 사진의 기존 pose에서 마커 방향을 추정했다. 독립 실측 geometry나 정답 pose가 아니다.

동일한 저장 trace 2,973프레임 비교 (`evidence/corner-report.json`):

| 지표 | 기존 중심 방식 | 모서리 가정 후보 |
| --- | ---: | ---: |
| 전체 중 계산 통과 | 102 (3.43%) | 1,240 (41.71%) |
| 0,1,2,4,5 조합 105개 중 통과 | 100 | 26 |

둘 다 통과 26, 기존만 통과 76, 후보만 통과 1,214, 둘 다 거절 1,657이다. 전체 2,973개 중 수치 모서리가 있는 프레임은 2,426개이며 나머지 547개에는 관측이 없다.

**전체 통과율 증가만 보고 후보를 채택할 수 없다.** 위 숫자는 실물 정합 정확도, 연속 화면 가용률, UI 깜빡임 개선률이 아니다. 고개 움직임과 준비 구간이 섞인 기록이다. 기준 사진에서 역투영한 변 길이 67.44~75.05mm 역시 실제 자로 잰 길이가 아니다.

### B. 눈별 보정 모델의 불안정성

- 눈별 독립 DLT는 눈마다 11 자유도다. 분석한 6점 세트는 fit 6 / 독립 check 0이었다.
- 해당 세트의 fit RMS는 왼쪽 1.475px / 오른쪽 2.201px지만, 투영행렬에서 해석한 눈 간격은 97.4mm였다. 실제 PD 측정치가 아니다.
- 같은 화면 좌표에 카메라 XYZ만 조금 다르게 대응시키면 해석된 간격이 크게 바뀌었다. 작은 fitting 오차만으로 정합 성공을 선언할 수 없다.
- PD 64mm를 soft prior로 사용하는 13-parameter 양안 비교 모델도 만들었다. 더 안정적인 경향은 있었으나 leave-one-pose-out 최대 오차 79.96px였고 독립 실물 검증을 통과한 모델이 아니다.
- 이 양안 비교 모델은 보고서용이며 실시간 활성 프로필로 내보내지 않는다.
- 사용자는 개별 수동 정렬에서 편하게 겹친다고 여러 차례 확인했지만, 중간에 안경을 올려 쓴 시점은 특정되지 않았다. 모든 세션을 같은 착용으로 합치면 안 된다.
- 저장 후 움직였다고 이미 저장된 JSON이 바뀌는 경로는 확인되지 않았다. 최종 PAIR는 같은 최신 관측에 양쪽 좌표를 묶고, 원 조절 시 저장 유효성을 해제한다. 시간 정합·pose 잡음·광학 모델·착용 변동의 기여는 여전히 구분할 필요가 있다.

### C. VITURE SDK 확인 결과

2026-10-07 실제 받은 패키지를 검토한 기록 기준이다. 최신 공개 제품 전체의 기능을 일반화한 설명이 아니다.

- Unity XR SDK 0.9.0: Android/Pro Neckband 경로, AAR. 해당 패키지의 Marker Tracking을 Windows Unity에 바로 붙일 수 있다고 확인하지 못했다.
- Windows Glasses SDK 2.4.0: 장치/표시 모드 조회 성공. 시험 조건에서 IMU 시작은 USB_EXEC(-3)로 실패했다.
- 사용자별 camera-to-eye/per-eye projection을 바로 제공하는 API는 확인하지 못했다.
- 따라서 현재 핵심 실행은 UVC/OpenCV + 자체 Unity SBS이며 SDK 기반 marker tracking/IMU 융합이 들어간 상태는 아니다.

## 8. 제안 중인 다음 순서: 확정 해법이 아니라 검토 대상

1. 검은 마커 외곽 크기·평면성·중심/회전 등록을 확인한다. 특히 이동한 4/5와 참조 사진에 없었던 3을 구분한다.
2. 실측 geometry로 저장 수치 비교를 반복하고, 기존에 잘 되던 조합의 손실 원인을 설명한다.
3. 근거가 확보되면 pose 계산과 observation 계약, Unity 소비 조건을 함께 연결한다. 먼저 고정 10초 + 작은 움직임 10초로 추적을 평가한다.
4. 추적이 안정된 뒤 같은 착용에서 A 기준/독립 자세를 검사한다. 실패하면 보정점을 무조건 늘리지 않고 오류 종류를 분리한다.
5. A 자동 표시가 검증되면 단계별 A-D 목표 원, 짧은 화살표, 얇은 나사 연결선 순서로 확장한다.
6. 단계 인식과 공간 표시의 일관성, 보류 이유, 연결 끊김을 포함한 시연 및 사용자 평가를 한다.

카메라 프레임/수치 관측/양안 픽셀 사이의 시간·좌표·착용 조건을 분리해 검토하고, 더 단순한 해결이 있으면 제안해 달라. 현재 계획을 방어하기 위한 검토는 아니다.
