# 인터넷 관제 기기 연결 검증

날짜: 2026-11-23. 범위는 로컬 후보 구현이며, 실제 Fold7 인터넷 연결 완료 보고가 아니다.

## 구현

- 휴대폰의 12시간 연결 코드 요청, 로그인한 소유자의 이름 확인·승인, 폰 전용 인증값 수신. 2026-11-24 사용자 요청으로 연장했다. 아래에는 이전 5분/15분 시도의 이력도 보존한다.
- 코드/비밀값은 DB에 해시로만 저장. 승인 중복 방지, 요청 용량·개수·빈도 제한, 만료·폐기 거절.
- Next.js `기기·설정` 화면에 코드 입력과 승인 UI 추가. 서버 비밀값과 폰 인증값은 웹 브라우저에 노출하지 않는다.
- Android 후보의 세부 검증은 `ANDROID_REMOTE_RESULTS.md`에서 관리한다. 기존 보정과 단계 판단 변경은 범위 밖이다.

## 독립 검토 반영

- 초기 viewer 검사 직후 승인을 지연하고 로그아웃을 완료하면 기기 발급이 성공하는 경합을 재현했다. 승인 SQL 안에서 viewer 행을 `FOR UPDATE`로 잠그고 유효한 viewer일 때만 pairing 갱신·기기 발급이 실행되도록 수정했다. 로그아웃과 같은 행의 잠금을 사용한다. 재현 회귀 테스트 통과.
- 인증 DB 조회 실패가 폐기와 같은 WS4401로 전달되어 Android에서 정상 토큰을 지우는 경로를 재현했다. 잘못된 자격증명은 4401로 유지하고 일시 서버 오류는 `1013 Authentication unavailable`로 구분한다. 서버 토큰 유효성 유지와 Android 재등록 없이 재접속 테스트 통과.
- 후속 검토에서 인증 DB가 5초 이상 지연되거나 다른 기기가 해제된 경우도 같은 삭제 정책에 걸리는 것을 재현했다. 인증 처리 중 타임아웃은 1013, 승인 세대 변경은 `4401 Reauthenticate`로 바꿨다. 인증 메시지 미수신은 기존 시간 제한을 유지하고, 실제 잘못된 토큰·만료·소유권 불일치는 영구 거절한다. 각각 재현 회귀 테스트 통과.
- 테스트 DB는 PGlite다. 별도 TCP PostgreSQL 여러 연결의 동시 트랜잭션·운영 프록시·TLS는 배포 단계의 확인 항목이다. 기기 Keystore는 후속 Fold7 계측 테스트 범위에서 통과했다.
- 최종 독립 재검토에서 인증 경계·회귀 테스트 5개 통과, 수정 범위 내 추가 결함 보고 없음. 상위 작업에서 전체 Node 64개 및 Android Gradle 빌드/검증 명령을 재확인했다.

## 미검증 / 다음 순서

1. 후보 APK 설치와 카메라 없는 계측 테스트 4개는 완료했다. 실제 연결 코드 승인과 앱 전환/재시작/관제 OFF를 먼저 확인한다. 현재 `adb reverse`를 통한 임시 로컬 경로이며 외부망 검증은 아니다.
2. 이어서 실제 안내 상태와 웹 표시, 네트워크 단절 시 AR 독립 실행을 확인한다.
3. EC2 전용 DB/relay + HTTPS/WSS, Vercel 웹과 운영 OAuth callback을 별도 배포한다.
4. Fold7 모바일 데이터와 노트북 Wi-Fi처럼 서로 다른 망에서 재연결·폐기·수신 지연을 확인한다.
5. 영상 송신/녹화는 별도 동의와 구현 후 진행한다. 현재는 상태만 전송하며 영상·음성은 전송/저장하지 않는다.

외부 서버 배포, git push, 카메라 활성화는 실행하지 않았다. 휴대폰 설치와 위 카메라 없는 실기 테스트만 후속 단계에서 추가했다.

## 2026-11-24 실제 승인 확인 및 재시작 실패

- 실제 GitHub 로그인을 갱신하고 사용자 제공 코드의 기기 이름 Fold7을 확인했다. 사용자가 앞서 허락한 승인 버튼을 눌러 등록했다.
- 웹에 `Fold7 연결을 승인했어요`, `연결됨`, `카메라 꺼짐`, `작업 대기`가 표시됐다. 마지막 수신은 한국 시간 12:14:56에서 12:15:05로 갱신됐다. 영상 전송/저장은 꺼짐. 실제 폰의 로컬 idle 수신까지 확인한 결과다.
- 이후 실제 HTTP 발급 결과를 측정하니 수명이 300초였다. 15분 수정 코드와 별개로 이전 relay PID 148048이 계속 실행 중이었다. 앞선 재실행 시도는 이미 사용 중인 포트 때문에 실패했다. health 200만으로 새 버전 적용을 판단한 것은 잘못이었다.
- 이전 프로세스를 Windows Stop-Process로 종료하고 새 서버를 시작했으나 PGlite가 `invalid resource manager ID in checkpoint record`, `could not locate a valid checkpoint record at 0/17E65D0`로 열리지 않았다. 현재 relay는 중단됐으며 재접속 검증은 미완료다.
- `.local/database` 원본을 유지하고 `.local/database-recovery-20261124`로 복사했다. 복사본에서도 debug:1로 동일한 실패를 확인했다. DB 초기화/삭제, WAL 강제 재설정, 토큰 재발급, 보정 변경은 하지 않았다.
- 원인은 비정상 종료 또는 이전 포트 충돌 재실행 과정의 동일 데이터 디렉터리 중복 열기와 관련될 수 있으나 둘 중 무엇이 손상을 일으켰는지는 확정하지 않았다. 공식 PGlite 이슈 #327/#884에서도 동일 오류와 NODEFS 종료 문제가 보고됐으나 이 사례의 직접 원인 증거는 아니다.
- 다음 조치: 원본 보존, DB 열기 전 중복 실행 방지, 정상 종료 경로 마련. 운영 PostgreSQL과 분리된 새 로컬 시험 DB로 다시 승인하는 방안은 사용자와 확인 후 진행한다. 기존 Fold7 승인 기록의 복구 여부는 아직 확인하지 못했다.
