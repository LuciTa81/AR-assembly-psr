# AR Assembly 1.4.1 인터넷 연결 상세

설명 대상은 Fold7 Android 앱, AWS EC2 중계, Vercel 웹이다. 기존 노트북 Python/Unity 버전은 별도이며 현재 휴대폰 실행에 필요하지 않다. 소스 및 운영 서버의 서비스/리스닝 포트/nginx 설정을 읽어 확인했다. 비밀값은 이 문서에 포함하지 않는다.

## 1. 역할과 실행 위치

| 구성 | 실행 위치 | 역할 | 하지 않는 일 |
|---|---|---|---|
| Android 앱 | Fold7 | 카메라 수신, ArUco 자세, YOLO 검출, 단계 안내, 눈별 투영, 렌더링, 선택적 영상 압축 | 서버에 인식 판단 위임 |
| Beast | 폰 USB-C 연결 | 작업대 카메라 입력과 양안 외부 디스플레이 | 인터넷 관제 서버 실행 |
| Nginx | EC2 | 외부 HTTPS/WSS 접속, TLS 종료, 내부 relay 전달 | AI 추론, 영상 디코딩 |
| Node.js/TypeScript Relay | EC2 | 폰/관제 인증, 기기별 메시지 전달, 상태 검증, 기록 처리 | AR 좌표/다음 단계 계산, 영상 녹화 |
| PostgreSQL | 같은 EC2 | 기기/세션/티켓/단계 이벤트 저장 | 영상 프레임 저장 |
| Next.js/BFF | Vercel | 웹 화면 제공, GitHub 로그인, 관제용 API 중개 | 실시간 영상 바이트 중계 |
| 관제 브라우저 | 노트북 또는 다른 PC | 상태 표시, H.264 디코딩, 영상 표시, 작업 기록 조회 | 폰 대신 AR 실행 |
| GitHub OAuth | GitHub | 사용자 신원 인증 | 작업대 영상 수신 |

## 2. 외부 진입점과 내부 연결

운영 EC2 주소는 `54.116.139.37`, 웹 주소는 `https://ar-assembly-supervisor.vercel.app`이다.

| 포트 | 현재 바인딩 | 용도 |
|---|---|---|
| TCP 443 | Nginx, 0.0.0.0 | 외부 HTTPS API와 WSS 상태/영상 연결 |
| TCP 80 | Nginx, 0.0.0.0 | ACME 인증서 검증 파일, 나머지 요청은 HTTPS로 308 전환 |
| TCP 8787 | Node relay, 127.0.0.1 | Nginx가 전달하는 내부 HTTP/WebSocket |
| TCP 5432 | PostgreSQL, 127.0.0.1 | relay가 사용하는 내부 DB 연결 |

경로는 `인터넷 -> Nginx:443 -> 127.0.0.1:8787 -> 필요한 경우 PostgreSQL:5432`다. DB와 relay 포트는 외부 주소에 바인딩하지 않는다. 위 표는 애플리케이션 관련 포트만 설명하며 SSH 등 EC2 전체 규칙을 열거한 것은 아니다.

TLS 1.2/1.3, Let's Encrypt 인증서, certbot 갱신 타이머가 구성되어 있다. Nginx는 WebSocket Upgrade를 전달하고 proxy buffering을 끈다. `/__local/` 경로는 외부에서 404로 막는다. `/health`는 인증 없는 서비스 상태 확인이고, 기기/기록 데이터는 인증 없이 제공하지 않는다.

## 3. 폰을 처음 연결할 때

1. 폰이 인터넷 관제 서버에 연결 요청을 만든다. 서버는 연결 코드와 별도 폴링 인증값을 발급한다.
2. 연결 코드는 12시간 유효하다. 코드를 아는 것만으로 관제 권한을 획득하는 것은 아니다.
3. 사용자는 GitHub로 관제 웹에 로그인한다. 허용된 본인 GitHub 숫자 ID인지 확인한다.
4. 브라우저가 Next.js BFF에 코드 조회/승인을 요청한다. BFF는 로그인 세션과 변경 요청의 Origin을 검사한다.
5. BFF가 서버 전용 서비스 키를 사용하여 EC2에 승인 요청을 전달한다. 이 키는 브라우저나 폰에 배포하지 않는다.
6. EC2는 승인된 폰에 30일 유효 기기 인증값을 발급한다. DB에는 평문 기기 인증값이 아니라 해시를 저장한다.
7. 폰은 Android Keystore 기반 AES-GCM으로 인증값을 암호화해 저장하고, 서버 주소에 묶어서 다른 서버로 잘못 보내지 않도록 한다.

연결 코드 12시간, 폰 인증 30일, 아래의 웹 접속 티켓 30초는 서로 다른 유효기간이다. 폰 인증이 만료/해제되면 다시 연결 승인이 필요하다.

## 4. 상태 관제 경로

`Fold7 -> wss://54.116.139.37/ws -> EC2 relay -> 관제 브라우저 /ws`

폰은 작업 중 250ms, 대기 중 1000ms 간격으로 상태를 추출한다. 단계, 주황/파랑/초록에 대응하는 phase, 행동 안내, 마커 수, RMS, 자세 관측 나이, 표시 여부, 작업 경과, 영상 공유 여부 등이 포함된다.

중계는 최초 WebSocket 메시지에서 폰 인증값 또는 관제 티켓을 검증한다. 폰은 publisher, 브라우저는 observer로 구분된다. 서버는 소유자/기기, 메시지 형식, 세션/순서 번호를 검사한다. 중복되거나 역순인 상태를 현재 상태로 덮어쓰지 않는다. 관제 사용자는 이 연결로 임의의 작업 상태를 발행할 수 없다.

서버는 받은 최신 상태를 메모리에 유지하고 해당 기기를 볼 권한이 있는 브라우저에 전달한다. 이 통신 주기는 카메라 입력 FPS나 폰의 AR 분석 주기와 다르다.

## 5. 웹이 실시간 연결을 여는 과정

1. 브라우저가 로그인된 Next.js API에 기기 목록을 요청한다.
2. 기기를 선택하면 `POST /api/observer/devices/{id}/ticket`을 요청한다.
3. BFF는 본인 세션을 검사하고 EC2의 `/devices/{id}/ticket`을 호출한다.
4. EC2는 해당 기기와 웹 세션에 묶인 일회용 티켓을 발급한다. 사용 전 유효기간은 30초다.
5. 브라우저는 이 티켓으로 EC2의 WSS에 직접 연결한다. 티켓은 한 번만 소비된다. 상태/영상 연결에는 각각 새 티켓을 얻는다.

30초마다 영상을 다시 연결한다는 뜻이 아니다. 30초는 아직 사용하지 않은 접속 티켓의 수명이다. 연결된 소켓은 권한 해제, 만료, 오류 및 heartbeat 조건에 따라 유지/종료된다.

## 6. 영상 관제 경로

`Beast 프레임 -> Fold7 MediaCodec H.264 -> wss://54.116.139.37/video -> EC2 relay -> 브라우저 WebCodecs -> Canvas`

기존 AR 분석은 200ms 간격의 별도 분기로 유지하고, 영상 압축은 카메라 입력에서 별도로 받는다. 목표 인코딩은 1280x720, 30fps, 약 2Mbps다. 목표는 측정값이나 보장이 아니다. 입력 프레임률, 폰 인코더, 발열, 네트워크, 브라우저 처리 성능이 실제 표시율에 영향을 준다.

영상 패킷에는 순서, 시간, 해상도, 키프레임 표시와 압축 데이터가 있다. EC2는 패킷 경계/크기/순서/권한을 검사하여 그대로 전달한다. 영상을 디코딩하거나 YOLO를 실행하지 않는다. 영상은 Vercel을 거치지 않는다. 이 구현은 WebRTC가 아니라 WSS/TCP이며 혼잡 시 지연 가능성이 있다.

현재 작업이 실행 중이고 상태가 신선하며 영상 공유 동의가 켜졌을 때만 전달한다. 별도 영상 소켓을 사용해 상태 메시지와 같은 큐에 쌓지 않는다. 느린 수신자에게 프레임을 계속 쌓지 않고, 누락 후에는 키프레임에서 복구한다. 기본 인코더 키프레임 간격은 1초이며 실제 복구 시간 보장은 아니다.

폰에서 영상 공유를 켜고 웹에서도 영상 표시를 켜야 보인다. 음성은 전송하지 않고 영상도 저장하지 않는다. 표시 영상은 카메라 시점이며, 안경의 양안 렌더를 합성한 영상이 아니다. 현재 운영 코드에 녹화 저장소/S3 저장 경로는 없다.

## 7. DB에 저장되는 것

| 테이블 | 내용 |
|---|---|
| devices | 기기 ID, 소유자, 이름, 인증 해시, 만료, 해제 상태 |
| pairing_requests | 연결 코드/폴링 인증 해시, 만료, 승인된 기기 |
| viewer_sessions | 관제 로그인 세션과 해제 상태 |
| tickets | 일회용 티켓 해시, 기기/소유자/세션, 만료 |
| events | 단계/phase 변화, 중단/복구 공백 등 의미 있는 상태 이벤트 |

모든 카메라 프레임이나 매번 받은 상태를 통째로 이력에 추가하지 않는다. 현재 상태는 실시간으로 전달하지만 DB 이벤트는 단계/phase 변화, 종료, 공백 등의 시점에 기록한다. 조회는 BFF -> EC2 `/devices/{id}/history` -> DB -> 브라우저 경로다. DB 쓰기가 실패하면 기록 불완전 상태를 표시하며, 이를 정상 기록으로 가장하지 않는다.

## 8. 끊김·로그아웃·서버 중단

- 상태 수신이 약 3초 이상 멈추면 stale로 보고 이전 영상/안내를 현재 유효한 것처럼 유지하지 않는다.
- 소켓 ping/pong으로 반쯤 끊긴 연결을 정리한다. 앱은 지수형 재시도와 지터를 사용한다.
- 웹 로그아웃은 해당 관제 세션과 티켓/소켓을 해제한다. 정상 폰의 기기 인증까지 삭제하지 않는다.
- 기기 연결 해제는 해당 폰 인증을 폐기하고 연결된 상태/영상 소켓도 닫는다.
- EC2나 인터넷이 끊겨도 로컬 AR 계산은 폰에 남는다. 인터넷 장애가 관제에 미치는 영향과 AR 병행 실기 안정성은 실제 시험에서 재확인해야 한다.
- 서버가 재시작되면 DB의 기기/기록은 남지만 이전 메모리 상태를 현재 실시간 상태로 복원하지 않는다. 폰이 재연결하여 새 상태를 보내야 한다.

## 9. 운영 배치와 한계

중계 systemd 서비스는 `ar-supervisor`, 현재 릴리스는 `/opt/ar-assembly/releases/20261124-03`이며 이전 `02`를 보존했다. PostgreSQL은 같은 EC2 안에 있고 RDS가 아니다. 현재는 단일 EC2이므로 고가용성/다중 서버 장애 조치가 구축된 구조는 아니다. NOVA는 이번 확인 시 inactive였으며 AR 업데이트에서 변경하지 않았다.

릴리스 전 DB 백업은 `/var/backups/ar-assembly/pre-video-20261124T144235Z.dump`에 있다. 이 백업이 있다는 사실을 별도 서버의 정기 백업/복구 훈련 완료로 해석해서는 안 된다. 인증서 갱신 타이머도 구성 상태와 장기 운영 검증은 구분한다.

## 10. 참고 GitHub 코드의 기여

기존 설계 기록에는 SafeOps의 화면/API/기록 분리 및 연결 지연 처리, sentientsys-web의 API 계층/관리자 인증/요청 출처 제한을 참고했다고 기록되어 있다. 회사 코드, 데이터, 비밀값은 복사하지 않았다.

확인 당시 SafeOps 상태 화면은 기본 5초 폴링이었으며 IVS 영상 코드는 별개였다. 현재 Node WebSocket relay, Android MediaCodec, WebCodecs 경로를 해당 저장소에서 그대로 가져온 것은 아니다. 현재 프로젝트에 맞는 최소 구성으로 새로 구현한 부분이다.
